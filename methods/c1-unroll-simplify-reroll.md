# C1 展开、化简、再分块（unroll, simplify, re-roll）

## 1. 一句话判断

引理边界如果是生成时随手留下的，而不是数学上的边界，那么把它们展开、跨边界化简、再按真正的复用重新切开，是减少命题个数的主要手段之一。这种边界在模型生成的大型开发里最多，人写研究仓库里少，维护者精心维护的库里引理边界本身就是对外接口，不该拆。单个定理上它就是内联 `have` 或抽引理，已有工具；到小仓库、大仓库上它是需要理解数学的结构性重写，中间状态没有保证。

## 2. 做什么

1. 固定最终陈述与证明骨架。
2. 把只用一次的引理、包装定义、命名的 `Prop` 内联，得到一条长而平的证明。
3. 在展开后的证明里找跨原边界的化简：重复的子推导、绕远的中间结论、可以直接用库引理的步骤。
4. 按真正被多处复用的结论重新切成引理，陈述写到自然的通用程度（[C2](c2-statement-generalization.md)）；切出的引理按实际复用次数验收，不按提出了多少条。
5. 单个定理上的同类操作：内联只用一次的 `have`，或把重复片段抽成辅助声明，每一步重编。

## 3. 谁在用

- 理论先例：切规则引入（反转切消，自动引入带量词的引理） [P17]、发明新定义来压缩证明 [P16]、在 HOL Light 的推理轨迹上挖可复用引理 [P18]、Mizar 的引理抽取 [P19]；HOL Light 的 Tactician 做 tactic 步骤的打包与展开 [P21]，带形式保证的重构定义见 [P20]。
- 以压缩为目标的库学习：Stitch、babble [P24] [P25]；反面证据是 *Library Learning Doesn't*：所学引理大多只用一次 [P27]。
- Lean 工具与基准：AXLE 的 `have2lemma` [P13]；Proof-Refactor 抽辅助声明，目标是结构和可读性而不是长度 [P28]；Leanify 压缩证明集合时，越往后的阶段发现越多非平凡引理 [P29]；LeanLean 的仓库级压缩大头来自依赖重组 [P30]（见 [repository-benchmarks](../cases/repository-benchmarks.md)）。
- 大仓库示例（Lean RH 开发，模型生成）：grh-lean（Luke Sernau 与 Anthropic 同事，借助 Claude） [D16] 的作者在 Zulip 上只给了一句方法描述，原意是把定义展开成长而平的证明，在那里找化简，再卷回去，这样可以跨边界化简 [z643710501]；具体流程没有公开。

## 4. 证据等级

- **有论文或工具**：自动引入引理、发明定义、证明内抽引理（[P13] [P16]–[P18] [P28] [P29]）。它们都在单个证明或证明集合上做，没有"先展开整个仓库再分块"的工具；Leanify、LeanLean 只读了摘要。
- **作者自述**：RH 案例里只有上面那一句，作者表示方法不能多说 [z643710501]。
- **推测**：RH 案例里重新分块确实发生了，这是我们从成品代码推断的（§7 的结构差异，见 [grh-compact-vs-original](../cases/rh/grh-compact-vs-original.md)）；具体流程、用了什么工具、多少由人多少由模型，都不知道。

## 5. 作用层级

单个定理到大仓库。单个定理与单个文件上是内联和抽引理，工具可做，不需要理解整段证明；小仓库、大仓库上是结构性重写，需要理解数学。来源上，只在边界由生成过程决定的代码上值得做。

## 6. 正确性靠什么保证

- 单步内联或抽引理：每步重编；形式定义的重构可以证明保持正确性 [P20]，但 Lean 里没有这样的工具。
- 整体重写只能靠最终闸门：陈述文件原样保留，用 comparator 与多个独立内核检查（[E2](e2-verification-gate.md)）。中间状态没有保证，所以必须在独立分支上整体完成，不能逐 PR 合并。
- （例：Lean RH 开发里，grh-lean 的两个版本都在发布当天由 MIT 用六个检查器核验 [D18]。）

## 8. 代价与坑

- 需要读懂整段证明；大仓库上只能保留骨架、分段重写，不可能逐行展开（例：Lean RH 开发的原始版本约 1,700 万行，从成品看是保留骨架重写的）。
- 展开后的中间证明可能极大，编译与内存成本高；只适合局部分段做。
- 切出的引理要按实际复用次数验收：模型提出的"可复用引理"大多没被复用 [P27]。
- 在精心维护的库里，不被内部引用的引理是对外接口（Mathlib 44.8% 的定理是叶子 [P38]），展开它们会破坏下游。
- 结果与原始代码几乎没有可对齐的名字，无法逐 PR 审阅（例：Lean RH 开发里紧凑版的声明名只有 14% 在原始版本出现过）。

## 9. 什么时候用

机械路线（A 层）到顶之后，而且只在引理边界明显由生成过程决定时（大量只有一个声明的文件、只用一次的引理、命名陈述）；与 [C2](c2-statement-generalization.md)、[C3](c3-unwrap-statement-layers.md) 同时做，之后接 [D3](d3-thin-then-thick.md) 为阅读展开。精心维护的库不用；人写研究仓库只在单个文件内做。

## 10. 未解决的问题

- 能否把"展开—化简—分块"做成半自动工具：展开由脚本做，化简交给模型，分块按复用度自动决定？
- 如何在中间阶段给出部分保证，使它可以分批审阅？
- 能否从结构指标（只有一个声明的文件比例、只用一次的引理比例）事先估计这条路线的收益？
- （RH 案例）缩小里本路线与换论证各占多少？从成品外部量不出来。
