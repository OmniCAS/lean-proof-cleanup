# lean-proof-cleanup

**Summary (English).** How to clean up, simplify and compress Lean 4 proofs without changing what is proved, at every scale from a single theorem to a repository of hundreds of thousands of files, and for every kind of source: a curated library such as Mathlib, a human-written research repository, proofs generated by a model, or a large development generated by a model. Provenance decides how much redundancy there is and of which kind, so it decides which routes pay off. The repository collects twenty-three cleanup routes in five tiers, one file each (`methods/`); a diagnosis step with source-level indicators measured on seven public Lean trees; cases indexed by scale and provenance (`cases/`); a survey of tools and literature across Lean, Coq/Rocq, Isabelle, HOL, Mizar and Metamath; a layered plan with a semantics-preserving gate (statements unchanged, no new axioms, kernel accepted); ranked ideas with an engineering pipeline; and a catalogue of datasets. Main findings: redundancy sits inside proofs for generated competition proofs (symbolic passes save about 20% of tokens, learned rewriters 57–87%) and almost nowhere in Mathlib (0.5%); in large developments it sits in the number of statements and their organisation, where repository-scale benchmarks find most of the gain in restructuring dependencies; mechanical cleanup is bounded by the share of dead and duplicate code, and larger reductions need rewriting with an understanding of the proof; every route needs the same gate, and its cost grows with scale. The large-repository, model-generated case is the November 2026 Lean development that states the Riemann Hypothesis and Dirichlet GRH (reported machine-checked by third parties; its mathematics is unreviewed), with its step-by-step community cleanup and the two-edition rewrite `lsernau/grh-lean`. The documents are in Chinese.

## 这是什么

给一个 Lean 仓库，怎样在**不改变它证明了什么**的前提下把它变小、变快、变得可读。两条轴贯穿全部内容：

- **规模**：单个定理 / 单个文件 / 小仓库（每批改动能全量重编）/ 大仓库。
- **来源**：精心维护的库（Mathlib）/ 人写的研究仓库 / 模型生成的证明（竞赛题等）/ 模型生成的大型开发。

这里放：

1. **路线** `methods/`：23 条清理与压缩路线，分五层：A 机械且保持陈述、B 逐个定理的局部改写、C 跨定理的结构重构、D 重写数学、E 所有路线共用的流程与闸门。总览 [`methods/README.md`](methods/README.md) 里有诊断指标、按规模与来源选路线的表和推荐顺序。
2. **案例** `cases/`：按规模 × 来源索引。单个定理 × 模型生成的证明；精心维护的库（Mathlib）；仓库级基准（LeanLean、Lean Refactor、Leanify）；大仓库 × 模型生成的大型开发（Lean RH 开发，`cases/rh/`）；以及七棵公开 Lean 树的结构指标对照（`cases/profiles.md`）。
3. **分层方案** `docs/layered-plan.md`：四个规模各自的目标、手段、语义不变的验证（G0–G6 闸门）与自动化程度。
4. **优化思路与工程流水线** `docs/ideas-and-engineering.md`：依赖图与可达性删除、去重、import 精简、批处理、增量与分布式构建、守卫、合并顺序、度量。
5. **调研** `docs/survey.md`、`docs/literature.md`，**数据集目录** `datasets/`，**待解决问题** `docs/open-problems.md`，**数据与脚本** `data/`、`scripts/`。

## 核心判断

1. **正确性来自闸门，不来自编辑器。** 不论改写者是 linter、符号 pass 还是 LLM，都要过"重新编译 + 陈述与公理比对 + 内核接受"。清理前先冻结裁判（导出一份 Challenge，之后用 `lake comparator --challenge-from-export` 判），否则可信定义被一起改时查不出来。
2. **冗余在哪里由来源决定。** 模型生成的竞赛证明，冗余在证明内部，符号 pass 就能省约两成；精心维护的库几乎没有可压的（LeanPolish 在 Mathlib 上 0.53%）；大型生成开发的冗余在命题个数与组织，仓库级基准的收益主要来自重组依赖（LeanLean）。
3. **机械路线有上限，更大的缩小要靠理解证明后重写。** 删死代码、去重、收窄导入的上限由死代码与重复的比例决定；越过它需要展开再分块、通用化陈述、去掉包装层、换论证。大仓库示例（RH）：机械清理估计至多两到三倍，在同一证明骨架上的重写把命题个数缩小了两个数量级。
4. **先诊断，再选路线；符号手段先于 LLM。** 只有一个声明的文件占比、每文件声明数、命名 `Prop` 定义密度、注释与导入占比能在不构建的情况下区分来源（`cases/profiles.md`）；确定性的 pass 可整库并行、几乎零成本，LLM 逐个改写定理是美元量级，碰不到命题个数。
5. **小仓库与大仓库的分界是"每批改动能不能全量重编"。** 大仓库要按依赖锥切片、只重编下游、按拓扑层分波并行、串行合并；能缩到整体重建的规模，核验才能从"构建通过"变成"多内核检查完"。
6. **指标要选对。** 总行数会被 import 展开和长行干扰，文件数会被合并干扰，源码长度与证明项大小可以反向；看命题个数、正文行、依赖闭包大小和冷构建 CPU 时间。

## 怎么用

```bash
# 给任意 Lean 源码树算结构指标（不构建），再汇总成只含计数的 JSON 与 CSV
git clone --depth 1 https://github.com/ImperialCollegeLondon/FLT.git downloads/FLT
python3 scripts/profile_lean_trees.py downloads/raw.json flt=downloads/FLT/FLT
python3 scripts/summarize_profiles.py --out downloads/profiles.json --csv downloads/profiles.csv downloads/raw.json

# 数据集目录与获取（只用标准库与 git）
python3 datasets/fetch.py list
python3 datasets/fetch.py fetch minif2f-lean4 --dest downloads

# 大仓库示例：RH 社区仓库各版本的规模统计（只读 Git 对象，不构建）
git clone https://github.com/leanprover-community/riemann-hypothesis.git downloads/rh
python3 scripts/rh_repo_stats.py --repo downloads/rh --out data
```

需要 Python 3.9 以上和 `git`。`downloads/` 已在 `.gitignore` 里。七棵树的版本与统计目录见 `cases/profiles.md`。

## 关于 RH 的说法

这里只说：这些 Lean 开发陈述了 Mathlib 的 `RiemannHypothesis` 与 Dirichlet L 函数的 GRH 形式，第三方报告机器核验通过，数学部分尚无人审阅。本仓库只构建了 grh-lean 紧凑版并打印了它的公理，没有构建其他版本，也没有运行 comparator。
